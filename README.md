# IRON DOME
### AI-Assisted Network Threat Monitoring and Incident Analysis

**IRON DOME** is a Python-based cybersecurity monitoring platform that integrates Suricata Intrusion Detection System (IDS) telemetry with Google Gemini Flash Lite for contextual security-event analysis. The project combines network threat monitoring, structured security-event processing, incident reporting, persistent incident history, and analyst feedback within a graphical application designed for cybersecurity laboratories and Raspberry Pi deployments.

The architecture separates deterministic network detection from probabilistic AI-assisted interpretation: Suricata provides rule-based detection, while Gemini analyzes supplied event context to help an analyst investigate and understand potential threats.

## Project Overview

IRON DOME is designed to provide a unified interface for monitoring security telemetry and assisting with incident investigation in controlled network environments.

The platform uses Suricata to inspect traffic visible to its configured capture interface and produce structured events. These events are written to the Extended Event Format (EVE) JSON log, which can serve as an input to application-level monitoring and analysis workflows.

The AI analysis component uses the Google Gemini API to interpret supplied incident information, summarize potentially relevant indicators, and provide investigative context. An incident-memory subsystem maintains historical observations and analyst feedback, allowing recurring event patterns and previous classifications to be included in subsequent analyses.

The system is intended for defensive network security experimentation, educational research, and small-scale monitoring prototypes.

### Design principles

- **Detection–analysis separation:** network detection and AI interpretation operate as distinct stages.
- **Structured telemetry:** security events are represented as machine-readable records.
- **Contextual investigation:** AI analysis incorporates event metadata and available historical context.
- **Human oversight:** analyst feedback supplements automated interpretation.
- **Deployment flexibility:** the application can be evaluated on desktop Linux/Windows environments and compatible Raspberry Pi systems.
- **Evidence-aware reporting:** observed events must be distinguished from inferred threats.

## Detection and Analysis Pipeline

### 1. Network telemetry acquisition

Suricata observes packets delivered to its configured network interface. Detection depends on interface selection, network topology, capture configuration, and the active rule set.

Depending on the enabled configuration and event types, Suricata can produce information about:

- Network flows and endpoint addresses.
- Protocol and connection metadata.
- Signature-triggered security alerts.
- Suspicious protocol behavior.
- Event timestamps and severity classifications.

A packet being captured does not necessarily mean that it will trigger an alert.

### 2. Structured event processing

Suricata's EVE JSON output provides structured records that downstream components can consume. IRON DOME can use event information to support monitoring and investigation workflows.

Relevant event attributes may include source and destination IP addresses, timestamps, alert signatures, and severity values.

Event processing must preserve the distinction between raw observations, IDS classifications, and subsequent AI-generated interpretations.

### 3. AI-assisted incident analysis

IRON DOME integrates Google Gemini through the Gemini REST API.

The application constructs an analysis request from supplied incident metadata and available historical context. The request is submitted to the configured Gemini model, and the resulting text is returned to the application for display.

The analysis workflow is intended to assist with:

- Interpreting IDS alert descriptions.
- Explaining potential security implications.
- Summarizing available incident context.
- Highlighting investigative considerations.
- Comparing current observations with recorded historical patterns.

Gemini output is an analytical aid, not an authoritative determination that an attack has occurred.

### 4. Incident reporting

The application combines network-security information with AI-generated interpretation to support incident investigation.

Reports should distinguish between:

- **Observed evidence:** packet metadata and recorded IDS events.
- **Detection result:** the signature or rule that generated an alert.
- **AI interpretation:** a model-generated explanation based on the supplied evidence.
- **Analyst assessment:** a human-reviewed classification or conclusion.

This separation helps prevent unverified model-generated conclusions from being represented as directly measured network facts.

## Incident Memory and Feedback

IRON DOME includes a persistent incident-memory subsystem backed by SQLite.

The memory component maintains incident records and human feedback that can be summarized for subsequent analysis. Historical aggregation includes recurring signatures, severity information, event counts, and previously assigned classifications.

### Memory capabilities

- Persistent incident-record storage.
- Aggregation of recurring signature patterns.
- Retention of analyst feedback.
- Retrieval of recent human-labelled examples.
- Inclusion of historical context in AI-analysis prompts.

Historical recurrence alone does not establish malicious intent. Similarly, a previous analyst label should be treated as contextual evidence rather than an infallible ground-truth classification.

## Installation

### 1. Install system packages

On Debian-based Raspberry Pi OS:

```bash
sudo apt update
sudo apt install -y python3 python3-venv python3-pip \
    suricata suricata-update jq
```

Install the PySide6 packages through the operating system's package manager if available, or use a compatible Python environment.

### 2. Create a Python environment

```bash
python3 -m venv --system-site-packages ~/iron-dome-venv
source ~/iron-dome-venv/bin/activate
```

Install the dependencies required by the committed application source. For example, if the environment requires PySide6 and keyring and compatible packages are available through pip:

```bash
python -m pip install PySide6 keyring
```

Do not install unnecessary packages simply because they were used by an earlier version of the application.

### 3. Install and update Suricata rules

```bash
sudo suricata-update
sudo suricata -T -c /etc/suricata/suricata.yaml
```

Resolve configuration or rule-loading errors before proceeding.

### 4. Configure Suricata

Ensure that the configured capture interface matches the interface that actually receives the traffic being monitored.

Start the service:

```bash
sudo systemctl enable suricata
sudo systemctl restart suricata
sudo systemctl status suricata
```

Check the EVE JSON log:

```bash
sudo tail -F /var/log/suricata/eve.json
```

The default path may differ depending on the operating system and Suricata configuration.

### 5. Place the application source

Copy the final IRON DOME Python source into the working directory on the target system.

For example:

```text
iron-dome/
└── IRON_DOME_GEMINI_ONLY_AUTO_IP_REGION_FIXED.py
```

The filename above is an example; use the actual filename committed to your repository.

## Gemini API Configuration

IRON DOME uses the Google Gemini API for AI-assisted analysis.

The application supports retrieving the API key from the operating-system credential store through `keyring`, with an environment-variable fallback.

Set the key in the shell before launching the application:

```bash
export GEMINI_API_KEY="YOUR_GEMINI_API_KEY"
```

Do not commit real API keys to the repository or embed them directly in the Python source.

The model identifier is configurable through the application's model configuration and/or `GEMINI_MODEL` environment variable, depending on the code path. Confirm that the selected model identifier is available to your Gemini API account.

The application sends requests to the Gemini `generateContent` REST endpoint. API access requires network connectivity, valid credentials, an available model, and compliance with applicable quota limits.

On Linux, the available keyring backend depends on the installed desktop or credential-store environment. If persistent credential storage is unavailable, use a suitable secret-management approach rather than assuming that the key has been saved permanently.

## Network Visibility Requirements

A network monitoring application can inspect only traffic that reaches its capture interface or is made available through a suitable traffic-mirroring arrangement.

In virtualized environments, traffic between virtual machines may remain within a hypervisor-managed virtual network. Connecting the Raspberry Pi to the same physical Windows PC does not automatically expose all VM-to-VM traffic.

For a VMware-based lab, use an explicitly configured and verified traffic path, such as:

- Routing the monitored traffic through the Raspberry Pi.
- Mirroring relevant traffic to a dedicated monitoring interface.
- Using an appropriate virtual-network monitoring arrangement.

Confirm packet visibility with a capture utility before troubleshooting IDS rules or GUI event processing.

For example:

```bash
sudo tcpdump -ni eth0
```

Replace `eth0` with the interface receiving the lab traffic.

Use only systems and networks that you own or are explicitly authorized to test. An isolated lab is recommended for validation.

## Security Considerations

### API credential protection

- Never commit API keys or access tokens.
- Use an appropriate credential store or protected environment configuration.
- Restrict access to application files and incident databases.
- Rotate exposed credentials immediately.

### AI output validation

- Treat model-generated analysis as untrusted explanatory output.
- Validate claims against actual IDS events and packet evidence.
- Avoid using AI-generated conclusions as the sole basis for incident escalation or blocking.
- Preserve human oversight for consequential security decisions.

### Defensive operation

- Validate firewall behavior before enabling any blocking functionality.
- Apply containment policies only to explicitly authorized lab or production assets.
- Avoid destructive traffic-generation tests against networks outside the controlled environment.
- Preserve relevant event logs for reproducibility and investigation.

### Privacy

Incident metadata can contain internal addresses, host identifiers, and sensitive operational information. Review the data sent to external AI services and transmit only the information necessary for the intended analysis.

## Limitations

IRON DOME is a monitoring and AI-assisted analysis prototype, not a replacement for a fully managed security information and event management (SIEM) platform or a validated network intrusion prevention system.

Important limitations include:

- Detection quality depends on Suricata rules, configuration and packet visibility.
- AI analysis is constrained by the completeness and accuracy of supplied event data.
- A detected anomaly is not necessarily evidence of a successful attack.
- A missing alert does not prove that traffic is benign.
- Gemini analysis requires API availability, credentials and network access.
- Historical incident patterns can contain false positives or incomplete labels.
- Raspberry Pi GUI compatibility depends on the operating system and display environment.
- Any automated blocking behavior must be independently validated and tested.
